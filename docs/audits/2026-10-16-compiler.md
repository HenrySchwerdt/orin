# Orin self-hosted compiler audit: cleanup potential and parallelism

Repo state audited: `main` at 1b8e1a8 (2026-10-16), read-only. `compiler/` is 84,340 lines of `.or`, of which about 440 KB / 31 lines is the generated
`compiler/loader/embedded_stdlib.or`, 13,332 lines are `compiler/tests/`, so roughly 69k lines are compiler logic.
All paths are relative to `/home/claude/orin`. Line numbers are from this checkout.

Measurements marked **[measured]** were taken here: I built the committed seed (`orin0`, `cc -O1`, 63 s), used it to compile `compiler/main.or`
(it succeeds, so the seed is current enough for HEAD), and profiled with `gprof` and wall-clock differentials. Scratch binaries were
not committed. Everything else is read from the source or the docs. Estimates are labelled as such.

---------------------------------------------------------------------------------------------------------------------------------------

## 0. Headline findings

1. **The compiler is already largely modern.** `docs/rewrite.md` records a rule-by-rule rewrite (rules 1-8). Counts over `compiler/` (tests excluded):
   about 1,735 `match` expressions, 697 `Option<>`, 436 `Result<>`, 675 `?;` propagations, 53 classes in 45 files, about 1,490 `@Requires/@Ensures/@Invariant`
   clauses, `Map<K,V>` in 17 files. The remaining old-style code is concentrated in a handful of files that the rewrite never reached
   (`check/index.or`, `vc/expr.or`, `vc/stmt.or`, `mcp/*`, `analysis/osig*.or`, `fmt/printer.or`, `check/classes.or`, `check/rthir.or`) and in
   copy-pasted helpers between modules.
2. **What the compiler does not use at all:** std:collections, std:seq, std:task, std:html/OX, generic functions or generic classes (0 of each outside
   tests), and `.sort()` (0 uses, while 7+ hand-written sorts exist). Only one `interface` exists (`BlockHost`, `check/expr.or:153`).
3. **Biggest cleanup wins by value/risk:** (a) shared helper modules for ~40 duplicated functions, (b) a generic HIR fold to replace ~13 hand-written
   HIR walkers (about 600 to 900 lines), (c) magic-int modes to unions (`FuncInfo.mode`, `FnCtx.fmode/cmode`, `Inst.kind`), (d) replace 7 hand-rolled sorts,
   (e) `main.or` pipeline and 7 hand-rolled CLI parsers, (f) rewrite `check/index.or` (2,356 lines, 3 contracts, parallel arrays, linear lookups).
4. **Parallelism is real but narrow.** Today's measurements: the MIR **verifier and optimiser are 70 to 90 % of an `orin compile`** and both are already
   shaped as per-function work (`docs/rewrite.md` "Rule 8"). The front end (parse 5 %, check 11 %) is not worth parallelising yet.
   Expected speed-up of `orin compile` on 4 cores: **about 1.4x (verifier only) to 1.7 to 2.1x (verifier + optimiser + lowering + emission)**.
5. **The real blocker is not threads, it is sharing.** Orin tasks have isolated heaps; a captured value is deep-copied per worker. **[measured]** a deep copy costs
   about 0.14 s per 0.9 M objects, so copying the MIR program (about 1.5 M objects, estimate) into each of 4 workers costs more than the verifier
   itself takes. ADR-0039 §"Hard gates" already names this ("`Env` and the program are frozen and borrowed by the tasks ... that is the real prerequisite").
   Either lend captured values (runtime work, coordinate with ADR-0038 "frozen sharing"), or pass each worker only its own function plus a small summary table
   (no runtime work, compiler refactor only).
6. **The largest wall-clock item in the build is not the compiler, it is `cc`.** **[measured]** `cc -O1` on the 11 MB generated C takes 63 s; the compiler emits it in 3 to 4 s. Splitting
   the emitted C into N translation units (the emitter is already per function, "rule 8") lets `cc` run in parallel for bootstrap, `orin test` and
   the test suite. It needs no language or runtime work.
7. **There is no global mutable state in the compiler** because the language has none (top-level `const` must be a literal). The sequential couplings that remain
   are explicit and listed in section 3.4.

## 1. What the seed allows (bootstrap constraints)

Sources: `docs/bootstrap.md`, `docs/bootstrap-subset.md` (historical), `seed/SEED_INFO`, `docs/known-limitations.md`, `tools/update_seed.sh`.

* `compiler/` is **no longer restricted to Orin-B**. It may use "any language feature the current seed can compile" (`docs/bootstrap.md`).
  The chain is seed (`cc`) -> orin0 -> orin1 -> orin2 -> stage3, and `stage2.c == stage3.c` must hold byte for byte; the LLVM fixed point
  (`tools/llvm_fixpoint.sh`) must hold too. Generated C "must not contain timestamps, absolute paths or hash-order-dependent output".
* The seed is `source-commit: 549ad51` (2026-10-16), 9 commits behind HEAD, and only workspace CLI commits are in between. **[measured]** the seed-built compiler compiled
  HEAD's `compiler/main.or` without problems, so the seed supports every feature HEAD's compiler supports. A feature the seed lacks needs a dedicated seed-refresh PR
  (`tools/update_seed.sh`).
* ADR-0046 (typed annotation processors) is still an open PR (#109), not in the tree. Annotations are ADR-0024: only `@Test`, `@Deprecated`, `@Inline`, `@Sealed` plus contracts
  (`@Requires/@Ensures/@Invariant`); user-defined annotations are post-1.0.

**Safe to use in compiler code today** (all implemented in the checker):

| Feature | Notes / limits that matter |
|---|---|
| tagged unions, nullary variants (the "enum"), `match` | `enum` is a reserved word; use `type K = A \| B \| C`. Exhaustiveness is checked. |
| `Option`, `Result`, `?` | `?` only inside a function returning `Result` with the same `E` (so `main`/`driver` returning `void` cannot use it). |
| classes (private members, invariants, mutating methods) | no inheritance, no static fields, no generic methods (E0460), a class cannot span files (`docs/rewrite.md:347`), a mutating call is hoisted and is rejected inside `&&`, `\|\|`, `?:` branches and `while` conditions (E0408). |
| interfaces (ADR-0019) | nominal, methods only, non-mutating only, no type parameters, boxed values (one allocation per conversion, indirect call): not for hot paths. |
| generic functions, generic classes with one `T extends I` bound (ADR-0007, ADR-0026) | instantiation depth <= 32 (E0413). |
| closures | capture by value only: **no mutation of captured variables**, no recursive arrows; array API `map/filter/some/every/reduce/find/findIndex/sort/forEach`. |
| `Map<K,V>` | keys only `int`, `usize`, `bool`, `string`; insertion ordered, so iteration is deterministic. |
| template literals | already used in `check/`, `loader/`, `cemit/`, `diag/`. |
| `std:collections` (IntSet, StringSet, Deque<T>, SortedMap<V> int keys, SortedStringMap<V>, PriorityQueue<T>), `std:seq` (3 functions), `std:task` | embedded in the compiler as `$stdlib` (`compiler/loader/prelude.or:91`). The stdlib is marked unstable, so a stdlib change can now break the compiler build: pin by tests. |
| OX / `std:html` | implemented (ADR-0043/0044), not used in the compiler yet. |

**Not available** (do not plan around them): generic methods (ADR-0040 accepted, E0460 still enforced), `Eq/Ord/Hash` bounds (ADR-0034 accepted, **no checker support**: so
no `Set<T>`, no `Map` with record keys, no `==` on unions/records, which is why `sameKey`, `isLocal` etc. exist), inheritance, top-level mutable state or array consts,
mutating captured variables, records/variants over 64 slots, import cycles (E0303: mutually recursive free functions must stay in one file or be cut with an interface/function value),
`async`/`await`, `Shared<T>`.

### 2.5 Smaller observations

* `check/checker.or:269-278`: the function loop is `env = o.env` threading. That is the structural reason the checker is sequential (section 3.4).
* `vc/vc.or:1238` and `:337`: a program-wide `qn` counter names the SMT files (`build/contracts-vc/...`). That is the only program-wide counter left in a per-function phase (ADR-0039 gate: "No global counters in a per-function phase").
* `check/expr.or` and `check/stmt.or` use an interface exactly once; `LspServer` (`lsp/handler.or:136`) and `McpSession` are good class-based designs to copy for A6.
* The verifier hot spot (not a cleanup, a performance finding): in the `gprof` profile `Transfer.load`, `killBorrows`, `Fixpoint.joinInto`, and `lsKind` (423 M calls) and
  `joinLs` (152 M calls) from `verify/state.or:86,174` dominate the self time. An algorithmic fix (word-parallel join, skipping unchanged blocks) is independent of parallelism and worth about as much as 2 threads.

### 2.6 How to keep every cleanup PR byte-identical (gates)

1. `tools/bootstrap.sh`: `stage2.c == stage3.c`, plus `tools/llvm_fixpoint.sh`.
2. **Fixed-point equality is not enough for a pure refactor** (a changed emitter still reaches a fixed point). Also compare the C of `compiler/main.or` and of a corpus produced by the
   pre-PR `orin2` and the post-PR `orin2` (`tools/differential.sh compilers` exists for this). A refactor of emitters/printers/diagnostic text must produce zero diff.
3. Per directory: `tools/protocol.sh lsp`, `protocol.sh mcp`, `test_osig.py`, `test_fmt.py`, `test_cli.py`, `run_tests.py` (the suites named in `docs/testing.md`).
4. Contract-bearing code: run `tools/test_compiler_contracts.sh` (the compiler built with `--check-contracts`) because several rewrites touch `@Invariant` text.

## 3. Part B: parallelism

### 3.1 What the language and runtime offer today

Sources: `docs/concurrency.md`, ADR-0017 (+Addendum A), ADR-0039, `stdlib/task.or`, `stdlib/taskcore.or`, `array/parallel.or`, `runtime/orin_runtime.c`, `docs/roadmaps/async-concurrency.md`.

| Facility | State |
|---|---|
| Tasks | `std:task`: `scope`/`scopeDo`, `spawn(s, f)` -> `TaskHandle<T>.join()`. A task is an **OS thread with its own heap**. A panic in a task traps the joiner (`task panicked: ...`). |
| Channels | bounded FIFO, blocking `send/recv`, explicit close (`stdlib/task.or:115-250`). |
| Fork/join | `forkJoin(chunks, workers, body: (k) => R): R[]` with work stealing (`Ranges` in `taskcore.or`), results in piece order; `forkJoinUntil`; `parallelMap(xs, f, parts)`; `parallelism()` (= `ORIN_THREADS` or processors online); with `workers <= 1` the pieces run on the calling task (`stdlib/task.or:770-817`). |
| `arr.parallel()` pipelines (ADR-0039) | `map/filter/reduce/some/every/find/findIndex`, fixed chunks of 4,096 elements, sequential below 8,192 elements (`array/parallel.or:34-35`), closures must be pure (E0484), input element must be a scalar or flat record of scalars (E0486). **Not usable for "one item per function"**: wrong granularity, wrong element type. Use `forkJoin` directly. |
| Delegating authority | `spawnFs/spawnProcess/spawnStdio/spawnClock` give a task its own grant (closures cannot capture grants, E0452/E0483). |
| Heap model | allocation, free lists, counters, grant and file tables are thread-local (`runtime/orin_runtime.c:11-12,365-384,1351,1633`); **reference counts are non-atomic**; the only shared state is the transfer slot table under the runtime lock (`:2009`), monitor words, two CAS-published immortal tables (`:500`, `:796`). |
| Crossing a task boundary | captured values, results, messages go through `orin_rt_transfer_put`: **moved** if every count in the graph is 1, otherwise **deep-copied**. A named local that is still alive counts as an owner, so it is copied. |
| Sharing | only *lending*: `orin_rt_lend` pins the input graph (counts frozen) while the workers run; used by `array/parallel.or` for the input array **only**. "Captured values of the closures are copied to every worker like any task body" (`array/parallel.or:30`). |

**Missing** for compiler-scale use:

1. **Shared immutable data**: no `Shared<T>`/frozen graph (ADR-0017 "post-1.0 option", ADR-0038 §"freeze/`Shared<T>`" and "frozen shared graphs" are planned, not built) and no way to lend closure captures. This is the prerequisite named in ADR-0039.
2. Per-task regions (a trapped task leaks its heap), cancellation beyond `rx.close()` and the pool's first-hit cancel, deadlock detection.
3. A Windows thread backend (`docs/windows.md`). Graceful fallback exists (`workers <= 1` runs inline), so any compiler use must keep an `ORIN_THREADS=1` path that is exactly the sequential code.
4. Deterministic trap ordering: "which element traps first is not defined when several would" (`array/parallel.or:26`). For the compiler this only matters for internal compiler errors, because user errors are `Result`s.
5. The compiler itself imports `std:task` nowhere (checked by grep). Linking is not a problem: the platform layer with threads is always linked into every program.

**Measured cost of the copy rule** [measured, `cc -O2`]: a program building 300,000 records (a record, a string and a 3-element array each, 0.9 M objects) and capturing the array in 4 spawned tasks
runs in 0.66 s, versus 0.09 s without the spawns: about **0.14 s per 0.9 M objects per copy** (150 ns per object), and the copies are made by the spawning thread one after the other. The optimised
MIR of the self-compile has 157 k instructions and 3,909 functions; at several objects per instruction that is on the order of 1 to 2 M objects (estimate). **Handing the whole `MProgram` to 4 workers costs
roughly 0.2 to 0.3 s per worker, serially, which is as much as the whole parallel part saves.**

### 3.2 Profile of an `orin compile compiler/main.or` (where the time goes)

Three views, which agree on the ordering. Total about 3.1 to 3.8 s with the `-O1`-built seed compiler [measured]; peak RSS 225 MB [measured]; 3,909 functions; 194 files; 11.4 MB of C.

(a) Callgrind instruction counts from `docs/rewrite.md:1386-1392` (36.4 G instructions): `optimize` 16.0 G (44 %), the verifier 15.9 G (44 %), `emitC` 0.8 G (2 %), everything else (loading, parsing, checking, fusing, lowering, pruning) about 3.7 G (10 %).

(b) `gprof` of an `orin1` built with `-pg` (no inlining, inclusive time, 2.58 s) [measured]:

| MIR verifier `verify` (3,909 `verifyFunction`) | 39.7 % | yes, loop at `verify/verify.or:493-501` |
| optimiser `optimize` | 29.3 % | of which per-function `optimizeFunction` 14.5 %, `unboxValues` 4.1 %, `pairReturns` 3.7 %, `dropUniqueProgram` 2.6 %, `inferModes` 1.9 %, `forwardProgram` 1.2 %, `uncheckProgram` 0.9 % |
| checker `check` | 11.1 % | no (section 3.4) |
| C emission `emitCFacts` | 5.7 % | yes, `emitCFunction(syms, prog, i)` |

(c) Wall-clock differentials with the `-O1` seed compiler [measured]: full compile 3.1 to 3.8 s; `--no-verify` saves 0.7 to 0.9 s; `--no-opt` (drops fuse+optimise) saves about 1.7 s; `--no-opt --no-verify`

Because the profile-instrumented build does not inline, the verifier looks bigger there (40 %) than in wall-clock terms (20 to 30 %). Use 25 to 45 % for the verifier and 30 to 45 % for the optimiser.

**Wall time of the whole bootstrap is dominated by `cc`:** compiling the 11.4 MB C of the seed took 63 s [measured], versus 3 to 4 s for the Orin compiler to produce it. Stages 0, 1 and 2 each pay that (`tools/bootstrap.sh`), and `orin test` pays a `cc -O1` per run (`testing/runner.or:221`).

### 3.4 Blockers in the compiler itself

* **No global mutable state** exists, by construction. Rule 8 (`docs/rewrite.md:617`, `:1312`) removed program-wide counters from per-function phases (C symbols, LLVM trap messages, lowering string table are
  computed first in a fixed order, then read-only), with unit tests that emit functions last to first and compare with the joined unit (`aCUnitIsTheJoinOfIndependentlyEmittedFunctions`,
  `anLlvmModuleIsTheJoinOfIndependentlyEmittedFunctions`, mutant 24). Per-function phases are therefore *already* parallel-ready at the algorithm level.
* **Remaining sequential couplings:** checker `Env` threading (`check/checker.or:269-278`); generic-instance and lifted-closure numbering; loader DFS file ids (`loader/loader.or:187-201`); `Rt.qn` in `vc/vc.or:337`;
  the optimiser's `ParamInference` fixpoint, `pairReturns` shapes and `unbox` web analysis (program-wide by nature); `Lits` pre-pass.
* **Shared mutable tables:** none shared between functions; all tables are classes or records with value semantics. The only sharing hazard is the large read-only `MProgram`/`Program`/`Env` captured by every
  worker: with isolated heaps it is **copied** (3.1), and with lending it would be **pinned** (counts frozen; a retain/release of a pinned object is a no-op, `docs/concurrency.md` "Soundness of lending").
* **Reference-count atomicity:** not needed as long as nothing is shared (non-atomic RC, thread-local heaps). It becomes a runtime question only if `Shared<T>` with atomic counts is chosen instead of lending. ADR-0038 plans "frozen sharing"
  as part of the same escape/region work: **do not invent a second mechanism; coordinate with the escape-analysis effort.**
* **Ordering of diagnostics:** user diagnostics are `Result` values built per function and merged by index (`dedupDiags`, `check/checker.or:316`); verifier errors are appended per function (`verify/verify.or:493-501`). Any parallel
  version must `forkJoin` over indices and merge in index order. `forkJoin` returns results in piece order, so this is natural.
* **Determinism of output:** pure per-function work gives identical results regardless of schedule; the `ORIN_THREADS=1..8` equality matrix of `tools/test_parallel.sh` is the right gate. The compiler's own internal
  errors would surface as `task panicked: ...` text (a changed ICE message, not a user-visible diagnostic).
* **Bootstrap:** the seed has `std:task` and `forkJoin` (the stdlib is embedded, `compiler/loader/prelude.or:91`), so using them needs no seed refresh. Threads add `-pthread` to the stage builds on older glibc (`tools/bootstrap.sh`
  `cc_link` passes no `-pthread`; glibc >= 2.34 and macOS do not need it), and Windows must run the `workers == 1` path.
* **Memory:** per-worker heaps multiply the live MIR if copying is used (RSS today 225 MB).

## 5. Risks and open questions

* **Gains are estimates** from a loaded machine and two different profilers; repeat the section 3.2 differential on an idle 4-core box, with `orin2` (`-O2`), before committing to P2/P3. The project's own docs record the same
  difficulty (`docs/concurrency.md` "Measurements").
* **Lend vs summaries (Variant A vs B)** is the one decision with long-term consequences; A is compiler-only and lets P2 to P5 proceed without the runtime team, B is cleaner but depends on ADR-0038 frozen sharing.
* **Splitting generated C (P1) changes output layout:** all emitter tests that compare whole units (`compiler/tests/emit_test.or`, `tools/differential.sh`, `tools/differential.sh compilers`) need to learn about multi-file output, or the single-file mode must stay available behind a flag (recommended: keep `-o out.c` as the single-file default and add `--jobs N`/`--split` so goldens stay valid).
* **Interfaces are boxed**: do not turn the optimiser passes or the verifier's `Transfer` into interface calls; the performance table in `docs/rewrite.md:1386` shows that +0.4 % was already a regression the team chased.
* **Hand sorts with contracts** (`analysis/modgraph.or:54`, `analysis/osig.or:108`) are `VERIFIED` obligations in places; replacing them with the prelude `sort` loses those proofs unless the postcondition is re-stated on a wrapper.
* ADR-0046 is still an open PR (#109); nothing here depends on it.
