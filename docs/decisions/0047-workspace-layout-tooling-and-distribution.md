# ADR-0047: Workspace layout, self-hosted tooling, reports and distribution

Status: proposed (2026-10-16)

## Motivation

Orin has a self-hosted compiler, `orin.toml`, LSP, VS Code support, native runtime, OX markup and a conformance suite, but the root mixes `compiler/`, `runtime/`, `platform/`, `std/`, `stdlib/`, `array/`, `seed/`, `editors/`, `tools/`, `bench/` and `spec/`. Onboarding and tooling depend on too many manual steps. The repository currently contains 39 Python files directly in `tools/`. This ADR defines a target design only, not an implemented migration.

## 1. Workspace manifests and package boundaries

- Introduce a validated root workspace manifest, provisionally `orin-workspace.toml`, plus a shared lockfile. Every actual Orin package has its own `orin.toml`: compiler, independent libraries, Orin-written tooling. Internal folders such as `compiler/syntax/` need not be separate packages.
- Support members/excludes, root dependency graph, package-scoped and whole-workspace build/check/test/fmt commands, deterministic build order and package-target constraints. Current single-project manifests and commands remain compatible.
- The manifest parser must reject unknown keys, missing members, duplicated names, traversal outside workspace, ambiguous path references, dependency cycles, incompatible targets and stale locked dependencies with clear source spans. No silent fallback.
- External packages keep their native manifests: VS Code uses `package.json`; an optional workspace tool declaration may point to it. No artificial `orin.toml` for JavaScript-only code.

Illustrative (not yet supported):

```toml
[workspace]
members = ["compiler", "runtime", "library/*", "tooling/*"]
exclude = ["tooling/vscode"]

[workspace.tools.vscode]
path = "tooling/vscode"
type = "npm"
```

## 2. Target repository layout

```text
orin/
  orin-workspace.toml
  orin.lock
  compiler/
    orin.toml
    syntax/ check/ hir/ mir/ lower/ opt/
    backends/c/ backends/llvm/       # later JS; WASM via LLVM target
    lsp/ fmt/ package/              # keep compiler-owned while appropriate
  runtime/
    core/
    platform/                       # platform-specific POSIX, later Windows/WASI
  library/
    core/                           # current std/
    std/                            # current stdlib/
    collections/                    # current array/
  tooling/
    conformance/
    benchmarks/
    reports/                        # report generator, OX templates and style assets
    codegen/
    verification/
    vscode/                         # package.json, no fake Orin manifest
  bootstrap/seed/
  tests/
  benchmarks/
  examples/
  formal/
  docs/
  scripts/
```

- This is an architectural mapping, *not* a directive to move every file at once or treat every folder as an Orin package. Preserve public `std:*` imports, module paths resolved by the toolchain, runtime ABI, seed integrity and packaged install layout.
- Distinguish compiler-trusted modules, L0 platform code, L1 runtime, normal standard library, tooling and external editor integration. Document source-to-release mapping.
- Keep formal independent checkers/proofs visible, and ADR/specification material discoverable in documentation. Large standalone ecosystem projects (e.g. web framework) belong in their own repositories once ready.

## 3. Self-host developer tooling, retain independent oracles

- Prefer Orin for first-party test runners, differential comparisons, mutation tools, benchmark harnesses, deterministic generators, report generation, verification orchestration and release helpers.
- Migrate the 39 existing `tools/*.py` based on observable feature parity, not file count: filters, expected diagnostic codes, exit codes, stdout/stderr, JSON, timeouts, parallelism, retries, negative tests, platform behavior. First `run_tests.py`, then `diff_backends.py`/`diff_compilers.py`, protocol tests, mutations, benchmarks and generators.
- `orin test` exists; proposed `--workspace`, `--conformance`, `--differential` and `--mutation` modes must be implemented and tested before advertised.
- Keep a minimal external seed/bootstrap (shell/C) and *independent* differential, verifier, solver and smoke-test oracles; do not let the self-hosted compiler be its only judge. Regular users must not need Python/Node just to install and run Orin.
- New Python scripts require a documented rationale (bootstrap, independent oracle, temporary migration), not a blanket ban.

## 4. HTML reports must be Orin + OX, with polished reusable design

All first-party HTML reports (benchmark comparisons, conformance/test results, mutation coverage, compiler diagnostics and verification/proof results, and future CI artifacts) SHOULD be generated by **Orin programs using OX**; once a report family is migrated, Python/Jinja, ad-hoc HTML concatenation and hand-coded JS templates MUST NOT remain its primary implementation.

- Put shared reporting primitives under `tooling/reports/` as an actual Orin package (with `orin.toml`): typed report model, common OX layout/components, and theme tokens; report producers pass structured data into that package, not HTML strings.
- Use `std:html` or a dedicated, type-checked OX provider; HTML escaping must be safe by construction. Do not bypass `@Sealed Html` or use arbitrary raw markup from test/log output. Sanitize/escape report content and safely constrain URLs. Avoid remote CSS/JS dependencies in offline CI artifacts.
- Default visual quality bar: refined, responsive report design, readable typography, intentional whitespace, restrained color palette, accessible contrast and focus states, dark/light support where feasible, clear status semantics (passed/failed/unproven/timeout), summary cards, sortable/filterable tables where useful, and readable code/diagnostic excerpts. Reports must still make sense without JavaScript; any progressive interactions are optional.
- Use a shared CSS design system distributed as a versioned local asset or safely embedded static CSS. CSS may be a generated/static asset; do not demand that OX generate every stylesheet declaration. The **HTML structure and data rendering** must be expressed in Orin/OX. No separate React/Node build is required to view a report.
- Require snapshot/golden tests of rendered output, escaping and HTML validity tests, large-data and empty-state tests, missing/invalid data tests, deterministic ordering, responsive visual regression screenshots or reviewed image baselines, accessibility checks and standalone/offline openability.
- Old report generators may coexist during controlled migration only with parity checks; report migration is not finished until its previous generator can be removed.

## 5. Strictness and CI quality gates

- Strict and fail-closed by default; reject malformed workspace TOML, unsupported backend constructs, invalid MIR, unsafe FFI casts and ownership errors. No successful build on unknown internal compiler states.
- Run MIR verification after transformations that may invalidate invariants; require positive, negative, fuzz and regression tests where relevant, C/LLVM differential behavior, compiler self-host fixpoint and reproducible release archives.
- Distinguish `proved`, `disproved`, `unknown`, `timeout`; never present unproven verification as proven. A project may explicitly require proofs for successful builds.
- Each file move or tool replacement must pass bootstrap stage2 == stage3, LLVM bootstrap checks, standard library tests, conformance diagnostics, platform/runtime boundary tests and applicable independent proof checks.

## 6. Installation, VS Code, releases and Homebrew

- First-run goal: install without a repository checkout; `orin doctor`, project generation, `orin dev`, editor intelligence work without manual LSP paths. Support `orin new` as a proposed alias/template UX; retain current `orin init`.
- Improve `orin` availability and toolchain discovery; preserve checksum validation and upgrade/uninstall semantics. CI must install/test on clean supported machines and clearly mark unsupported platforms.
- Publish VS Code extension on Marketplace with automatic installed-compiler discovery and compatibility checks, actionable errors, and iterative code actions, imports, signature help, semantic tokens, inlay hints, test explorer, debugger and verifier-status features. Preserve editor-independent LSP.
- Create a **separate** `orin-lang/homebrew-orin` tap in a later PR, enabling `brew install orin-lang/orin/orin` once published. Pin actual release URLs/SHA256, package all required runtime/platform assets, test `--version`, `doctor`, compile/run, install/upgrade/uninstall. Automate formula update PRs from published release artifacts.
- Start with the macOS ARM64 artifact that actually exists; support Intel only once release binaries and smoke tests exist. `brew install orin` without a tap requires eventual homebrew-core acceptance and is not claimed here.
- Align compiler, runtime/stdlib artifacts, editor and tap versions. Document compatibility and provide explicit mismatch diagnostics.

## 7. Incremental migration sequence

1. Workspace manifest syntax/semantics ADR detail and failcase fixtures; no moves.
2. Implement workspace resolution/CLI and common lockfile; preserve standalone projects.
3. Migrate libraries/runtime/platform in small path-only PRs and verify ABI/import compatibility.
4. Consolidate compiler backends and bootstrap assets; verify both self-hosting fixpoints.
5. Port conformance and differential harnesses to Orin, with independent parity checks; gradually remove Python.
6. Create shared OX report package, style system, and migrate HTML reports individually with output, safety and visual parity tests.
7. Publish improved VS Code editor and streamlined first-run flow.
8. Create external Homebrew tap, connect release updates and test supported platforms.

Each phase must be independently reviewable and revertible; do not combine semantic compiler changes with bulk renames.

## Non-goals / acceptance

This ADR does not implement workspace syntax, move existing code, remove Python, create a tap, or introduce the JS/WASM backends. Completing the initiative requires reproducible full-workspace builds, backwards compatible public imports, intact compiler/runtime trust boundaries, equal or better negative test coverage, polished offline-readable OX-generated reports, tested install channels, and functioning editor integration.
