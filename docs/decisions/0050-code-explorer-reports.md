# ADR-0050: The code explorer: an offline, OX-generated report of the code, its processes and its changes

Status: proposed (2026-10-16). Builds on ADR-0047 section 4 (reports are Orin + OX on `orin-reports`), ADR-0023 (OSIG schema and versioning) and ADR-0037 (effects).

## Motivation

`orin graph` already knows everything a reader wants to see about a package: modules, symbols, signatures, calls with MUST / MAY / UNKNOWN evidence, contract clauses, transitive effects. `orin diff` explains the difference between two states. Both end in JSON or in a flat text/HTML dump. There is no place where one can *look around*: see the module structure, follow a call, read a symbol's documentation next to its contracts and effects, or review a pull request as a picture of what changed.

The explorer is that place. It is a report (ADR-0047 section 4): generated by an Orin program with OX, safe by construction, offline, deterministic, tested against goldens.

## Decision

### 1. What it is

`tooling/explorer` (`orin-explorer`, depends on `orin-reports`) is a command, `explore SNAPSHOT.json [--diff DIFF.json] [--title NAME] --out DIR`, that turns an OSIG snapshot (and optionally an `orin diff --format=json` report) into a static multi-page site. It reads files only; it never runs the compiler (a wrapper does: `orin graph pkg -o s.json`, `orin diff --base A --head B --format=json -o d.json`, `explore s.json --diff d.json --out site`). One input pair gives one site; the same pair always gives byte-identical files.

### 2. Views

| View | Content | Data |
|---|---|---|
| Overview | summary cards (modules, symbols, calls, contracts, effectful functions, documentation coverage), the module dependency graph, a module table, most-called symbols | snapshot |
| Graph | module imports (transitive reduction: shortcuts implied by a longer path are not drawn, the count is stated) and module call flow (strongest flows, line width = calls, style = evidence), both as server-side laid-out SVG | snapshot |
| Module page | statistics, imports and imported-by, the module's top-level symbols | snapshot |
| Symbol page | signature, flags, documentation comment (TSDoc: paragraphs, code, `@param` / `@returns` tags), contract clauses, effects with evidence and the callee they are inherited from, members, a call neighbourhood graph, callers and callees with evidence and first call site, type references | snapshot |
| Symbol index | every symbol with a page, filterable | snapshot |
| Processes | the compiler pipeline parse, load, check, HIR, MIR, optimise, verify, emit with the size, contracts and effects of the modules that implement each stage; the effects of every entry point | snapshot now; CI run history later (step 3) |
| Changes | added / removed / changed symbols, contract clauses, possible renames, edges, effect changes, new and removed call paths with the entry points that reach them, impact | `orin diff` JSON |

Evidence is always shown as text (MUST / MAY / UNKNOWN badge, with the meaning as tooltip), never by colour alone; in graphs it is also the line style (solid, dashed, dotted).

### 3. Rules

- **HTML and data rendering in Orin / OX.** Pages are OX components over typed records; the explorer builds no HTML strings. Every dynamic string is a `string` child or attribute of `std:html` and escaped there; URLs go through the `href` rule of the provider. The only trusted markup is the SVG of the graphs, which is a sealed `SvgDoc` built by `orin-reports`' `Canvas`: its methods escape text and tooltips, reduce class names to `[a-z0-9_ -]` and accept link targets only if they are relative (no scheme, no `//`, no quote or angle bracket).
- **Works without JavaScript.** Every page is complete and navigable with scripting off. The one optional script, `assets/explorer.js` (about 80 lines, a file of the site, not inline), adds a symbol filter, drag to pan and ctrl-wheel zoom on graphs, and a fit-to-width button. No network, no storage, no `eval`. Pages contain no inline script, no inline style and no event-handler attributes; the stylesheet is `assets/explorer.css` (the shared theme plus the explorer's own rules), so thousands of symbol pages do not repeat 20 KB of CSS.
- **Offline, no remote resources.** Only relative links; the test suite checks that every link of every page resolves to a file of the site.
- **Deterministic.** Snapshots are sorted by id; every list is sorted with a total order; slugs are lower-case, unique after case folding (`Token` and `token` do not collide on macOS) and assigned in node order. The graph layout has no randomness. No timestamps, no paths of the build machine.
- **Safe on hostile and huge input.** Unknown fields are ignored, a missing field has a default, a wrong schema family is refused with a diagnostic and nothing is written. Long tables are capped with a statement of how many rows are not shown. The compiler itself (3,800 symbols, 22,000 edges, a 6 MB snapshot) renders in about a second.
- **Tests.** Golden site of a fixture package (`testdata/golden`, regenerated by `testdata/regen.sh`, which also checks that the committed snapshots are what `orin graph` writes today), escaping of `<script>&"'` in names, signatures, documentation, contracts, effects and diff text on every page, empty diff, determinism, slug uniqueness, refused inputs, layout properties, link resolution. Run by `tooling/explorer/test.sh`, which `tools/test_tooling.sh` runs.

### 4. The graph layout

A deterministic layered layout, left to right: cycles are broken by a depth-first search (the closing edge is drawn backwards), layers by longest path with sources pulled next to their targets, long edges get dummy vertices, crossings are reduced by alternating barycenter sweeps, and heights are fitted by an isotonic regression (pool adjacent violators) that keeps order and spacing and moves each node toward the mean of its neighbours. Edges leave and enter a node at separate heights ordered by the other end. Edges are cubic curves with horizontal tangents. Nodes are rounded boxes with an accent bar (blue: has contracts, amber: may perform effects) and an `IO` mark. The layout is a pure function in `layout.or`, tested without any HTML.

### 5. Documentation comments (compiler change)

Documentation comments were not part of the snapshot. Two options: let the explorer re-read the sources next to the snapshot, or put the comments into the snapshot. The second keeps a snapshot self-contained (a snapshot from last month still explains itself, and two snapshots can be diffed without the sources of either), and reuses the one implementation of "which comment documents which declaration" (`analysis/doccomments.or`, the one the LSP hover uses). So `osig/0.3` adds the node field `doc` (the rendered `/** */` text, written only when present; `orin graph` scans each file's comments once). Schema history, ADR-0023 rules: additive, minor version bump, readers ignore what they do not know, every `osig/0.*` snapshot is still read. Only `/** */` comments attach (as in the hover); the `//` comment convention of the compiler's own sources is deliberately not treated as documentation, and the explorer reports the resulting coverage (the compiler: close to 0 %), which is a finding, not a bug.

### 6. Staged plan

1. **This step.** Package, views above, `osig/0.3`, tests, demo for the compiler and for a fixture.
2. **CI wiring.** A workflow step builds `explore`, runs `orin graph` / `orin diff` for the pull request's base and head and publishes the site as an artifact next to the benchmark report; `--link-base` style source links. Diffs of documentation comments in `orin diff` (the `doc` field makes it a small addition).
3. **Processes with data.** Run history from CI: per-stage and per-module compile times from `orin --time`, test, conformance and proof outcomes per module, with the status vocabulary of `orin-reports` (passed, failed, unproven, timeout, regression). A `--process-map` file so other packages can name their own stages.
4. **Navigation.** A client-side search over a generated index, call-path queries ("how does `main` reach `Fs.WriteFile`"), a source viewer with spans, side-by-side graph diff (added and removed nodes and edges drawn in one picture).
5. **Other families.** The conformance, mutation and diagnostics reports reuse the shell, the table components and the canvas; the explorer's graph components move into `orin-reports` when a second user exists.

## Consequences

- One more package and one more OSIG minor version; the snapshot grows by the documentation text only.
- `orin-reports` gains a page shell with extension points (`ShellWith`), a bare SVG canvas with links and rounded boxes, and polishes the card grid for every report: a number never wraps inside a card (short form with the exact value as tooltip), and the grid has no orphan row.
- The explorer shows what the analysis knows and nothing else: effects and calls are the OSIG's, with its limits (calls through function values are UNKNOWN; the std prelude is not loaded).

## Non-goals

A source editor, a language server, live updates, anything that needs a server, remote fonts, or a JavaScript framework.
